# AvtoCars: Практична робота 1

Чиста архітектура та Domain-Driven Design на прикладі автосалону (ASP.NET Core, .NET 8).

## 1. Предметна область

Програмна система **автосалону**: облік автомобілів, що продаються, та оформлення їх продажу.
Предметна область обрана тому, що в ній природно виникає кілька різних "поглядів" на одну й ту саму сутність (авто): для продажів, для сервісного обслуговування, для складу запчастин. Це добре ілюструє поняття bounded context.

## 2. Архітектура

Рішення складається з чотирьох окремих проєктів (шарів):

```
AvtoCars.sln
├── AvtoCars.domain          // ядро: сутності, Value Objects, бізнес-правила
├── AvtoCars.Application     // сценарії використання, інтерфейси (абстракції)
├── AvtoCars.Infrastructure  // EF Core, SQLite, реалізація репозиторіїв, міграції
└── AvtoCars.Api             // ASP.NET Core Web API (контролери, Swagger)
```

### Правило залежностей

Залежності спрямовані лише всередину, до Domain:

```
Api  ->  Application, Infrastructure
Infrastructure  ->  Application
Application  ->  Domain
Domain  ->  (нічого)
```

- **Domain** не містить NuGet-пакетів і не залежить від жодного фреймворка (використовується лише `System`).
- **Application** оголошує інтерфейс `ICarRepository`, але не знає, як саме зберігаються дані.
- **Infrastructure** реалізує `ICarRepository` через Entity Framework Core (клас `CarRepository`).
- **Api** містить тонкі контролери: вони лише приймають HTTP-запит і викликають сервіс з Application. Бізнес-логіки в них немає.

Зв'язування абстракцій з реалізаціями виконується через Dependency Injection у `Program.cs`:

```csharp
builder.Services.AddScoped<ICarRepository, CarRepository>();
```

## 3. Доменна модель (DDD)

| Елемент | Тип у DDD | Опис |
|---|---|---|
| `Car` | Entity, коренева сутність (Aggregate Root) | Має ідентичність (`Guid Id`), ціну, VIN і стан продажу |
| `Vin` | Value Object | VIN-код авто; конструктор перевіряє, що довжина дорівнює 17 символів |
| `Money` | Value Object | Сума (`Price`) і валюта (`Currency`), незмінні після створення |

Бізнес-правило живе в домені, а не в контролері чи репозиторії:

```csharp
public void Sell()
{
    if (IsSold == true)
        throw new InvalidOperationException("Авто уже продано");
    IsSold = true;
}
```

Властивості мають `private set`, тому змінити стан об'єкта в обхід методів домену неможливо.

## 4. Bounded context

### Sales (Продажі), реалізовано

- Сутності та об'єкти: `Car`, `Vin`, `Money`.
- Відповідальність: облік авто в продажу, оформлення продажу, захист від повторного продажу.
- Сценарії (Application): `AddCarServices` (додати авто), `SellCarServices` (продати авто).

### Service (Сервісний центр), описано

- Те саме авто тут представлене іншою моделлю `Vehicle`: VIN, пробіг, історія ремонтів, гарантія.
- Відповідальність: запис на обслуговування, ремонтні замовлення, гарантійні випадки.

### Inventory (Склад запчастин), опційно

- `Part`, `Supplier`, `StockItem`: залишки, резервування деталей під ремонт.

### Взаємодія між контекстами

Контексти не звертаються до баз даних одне одного. Обмін відбувається через явні контракти:

- Спільний ідентифікатор між контекстами: **VIN**.
- Коли Sales продає авто, він публікує подію `CarSold` (VIN, дата, ціна).
- Service отримує цю подію (або дані через DTO/API) і створює у своїй моделі `Vehicle` з гарантією.
- Service не змінює стан `Car` у Sales; кожен контекст володіє лише власною моделлю.

## 5. Обґрунтування архітектурних рішень

- **Окремі проєкти замість папок.** Якщо в Domain немає посилання на EF Core чи ASP.NET, написати залежність від них неможливо: збірка видасть помилку. Правило ізоляції контролює компілятор.
- **Інтерфейс `ICarRepository` в Application.** Application залежить від абстракції, а не від бази даних. Базу можна замінити (SQLite на SQL Server) без зміни бізнес-логіки (принцип інверсії залежностей).
- **`Vin` і `Money` як Value Objects.** Валідація виконується в момент створення, тому в системі не існує некоректного VIN. Це також захищає від плутанини примітивних типів.
- **Приватні сеттери та метод `Sell()`.** Інваріанти захищені всередині сутності.
- **Тонкі контролери.** Усі рішення приймає домен, контролер лише передає запит далі.
- **Окремий приватний конструктор у `Car`, `Vin`, `Money`.** Потрібен тільки EF Core для відновлення об'єктів з бази, назовні не видимий.

## 6. Відповіді на контрольні питання

1. **Основна ідея чистої архітектури.** Бізнес-логіка не залежить від фреймворків, бази даних і UI; залежності спрямовані до центру (Domain).
2. **DDD та його роль.** Підхід до моделювання складної предметної області на основі спільної мови з експертами; дає інструменти (Entity, Value Object, Aggregate, Bounded Context) для структурування складності.
3. **Призначення bounded context.** Визначає межі, в яких модель і терміни мають єдиний узгоджений зміст; за межами контексту той самий термін може означати інше.
4. **Дозволені залежності між шарами.** Лише до внутрішніх шарів: Api -> Application, Infrastructure; Infrastructure -> Application; Application -> Domain. Domain ні від чого не залежить.
5. **Чому домен ізольований від інфраструктури.** Бізнес-правила живуть довше за технології; ізоляція дає змогу змінювати БД і фреймворки без переписування логіки та тестувати домен без бази даних і мережі.

## 7. Технології

- .NET 8, ASP.NET Core Web API
- Entity Framework Core 8 (SQLite)
- Swagger (Swashbuckle)

## 8. Запуск

Файл бази даних (`*.db`) не зберігається в репозиторії, його створюють міграції.

```powershell
# з кореневої папки рішення
dotnet ef database update --project AvtoCars.Infrastructure --startup-project AvtoCars.Api
dotnet run --project AvtoCars.Api
```

Потрібен інструмент `dotnet-ef` версії 8.x:

```powershell
dotnet tool install --global dotnet-ef --version 8.0.11
```

Після запуску відкрийте Swagger за адресою, яку покаже консоль (наприклад `https://localhost:7052/swagger`).

### API

| Метод | Адреса | Опис |
|---|---|---|
| POST | `/api/cars` | Додати авто, повертає `{ "id": "..." }` |
| POST | `/api/cars/{id}/sell` | Продати авто |

Приклад тіла для `POST /api/cars`:

```json
{
  "vinCode": "1HGCM82633A123456",
  "price": 500000,
  "currency": "UAH"
}
```

### Перевірка бізнес-правила

1. `POST /api/cars` повертає `id`.
2. `POST /api/cars/{id}/sell` повертає `200`.
3. Повторний `POST /api/cars/{id}/sell` з тим самим `id` повертає `500` з повідомленням `Авто уже продано`: правило спрацювало в `Car.Sell()` у Domain.

## 9. Плани розвитку

Наступні практичні роботи розширюватимуть цей проєкт: обробка помилок (наприклад, `409 Conflict` замість `500`), події домену, другий bounded context та рефакторинг відповідно до нових патернів.
